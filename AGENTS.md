# AGENTS.md

## Проект

`Learny` — личная платформа `londxz` для подготовки к iOS-собеседованиям и изучения Go. Текущий frontend уже реализован на React/Vinext и опубликован через OpenAI Sites/Cloudflare. Следующая крупная задача — перенести учебный контент, вопросы, задачи, интервью и прогресс из захардкоженных данных и `localStorage` в полноценный backend на Go.

Этот файл фиксирует согласованную архитектуру и порядок разработки. Более новые явные пожелания пользователя имеют приоритет над этим документом.

## Цель backend

Backend должен стать единственным источником истины для:

- направлений iOS и Go;
- форматов «Подготовка к собеседованиям» и «Учебный план»;
- разделов, модулей, тем и уроков;
- теоретических вопросов;
- задач для лайвкодинга, стартового кода, тестов и эталонных решений;
- мок-интервью и выбранного пользователем количества заданий;
- ответов, попыток, прогресса и истории запусков;
- порядка отображения и статуса публикации материалов.

Добавление и изменение контента должно выполняться через закрытую админ-панель Learny, без правок исходников frontend и ручного редактирования базы.

## Архитектурное решение

### Общая схема

```text
Browser
  -> Learny frontend / same-origin API routes
  -> Go API
  -> PostgreSQL

Go API
  -> сервис безопасного запуска Swift/Go
```

- Текущий frontend и его `.openai/hosting.json` сохраняются.
- Новый Go backend размещается как отдельный сервис, потому что Sites/Cloudflare Worker не запускает постоянный Go-процесс.
- PostgreSQL используется вместо D1 как основная база Go backend.
- Browser не должен напрямую получать секрет backend или доверенные служебные заголовки.
- Frontend обращается к собственным `/api/*` route handlers. Они выступают тонким BFF/proxy к Go API, передают проверенную пользовательскую идентичность и скрывают внутренний адрес сервиса.
- `localStorage` остаётся только для временного черновика редактора и неавторитетных UI-настроек. Контент и прогресс в нём больше не хранятся.
- Существующий `/api/run` и публичный Judge0 допустимы только как временная реализация до переноса запуска кода под контроль Go API.

### Backend-стек

- Go с обычным `net/http` и лёгким роутером `chi`.
- PostgreSQL.
- `pgx` для подключения к PostgreSQL.
- SQL-миграции через `goose`.
- SQL-запросы через `sqlc`, без тяжёлого ORM.
- OpenAPI как контракт между frontend и backend.
- Структурированные JSON-логи через `slog`.
- Конфигурация только через environment variables.
- Локальная разработка PostgreSQL через Docker Compose; сам Go API должен также запускаться обычной командой без обязательного контейнера.

Не добавлять микросервисы, брокер сообщений, Redis, Kubernetes и GraphQL до появления практической необходимости.

## Структура backend

Backend размещается в этом же репозитории:

```text
backend/
  cmd/api/main.go
  internal/
    config/
    httpapi/
    auth/
    catalog/
    content/
    interview/
    progress/
    runner/
  migrations/
  queries/
  openapi/
  go.mod
```

Правила слоёв:

- HTTP handlers отвечают только за разбор запроса, авторизацию, валидацию и формирование ответа.
- Бизнес-правила находятся в сервисах соответствующего домена.
- SQL находится в `queries/`, а сгенерированный `sqlc`-код не редактируется вручную.
- Доступ к базе не должен быть размазан по handlers.
- Доменные ошибки переводятся в единый формат API-ошибок.
- Все идентификаторы публичных сущностей — UUID.
- Все даты сохраняются в UTC.

## Модель данных

### Контент

1. `users`
   - идентификатор внешнего пользователя;
   - email;
   - роль `admin` или `student`;
   - timestamps.
2. `directions`
   - `ios` и `go`;
   - название, slug, позиция, статус публикации.
3. `tracks`
   - принадлежат направлению;
   - тип `interview` или `learning`;
   - название, описание, позиция, статус публикации.
4. `sections`
   - принадлежат треку;
   - название, описание, позиция, статус публикации.
5. `topics`
   - принадлежат разделу;
   - название, описание, позиция, статус публикации.
6. `lessons`
   - принадлежат теме;
   - теория в Markdown, длительность, позиция, статус публикации.
7. `questions`
   - принадлежат теме;
   - формулировка, пояснение/эталон ответа, сложность, позиция, статус публикации.
8. `coding_tasks`
   - принадлежат теме;
   - язык `swift` или `go`;
   - условие в Markdown;
   - стартовый код;
   - эталонное решение;
   - лимиты времени и памяти;
   - сложность, позиция, статус публикации.
9. `coding_task_tests`
   - принадлежат задаче;
   - stdin/ожидаемый stdout или runner-specific payload;
   - признак скрытого теста;
   - позиция.
10. `tags` и `content_tags`
    - нужны для фильтрации и генерации сбалансированных интервью.

### Прогресс и интервью

1. `user_progress`
   - пользователь, тип и ID материала;
   - статус `not_started`, `in_progress`, `completed`;
   - timestamps и последняя позиция.
2. `interview_sessions`
   - пользователь, направление, режим `theory` или `livecoding`;
   - выбранное количество;
   - статус, начало и завершение.
3. `interview_session_items`
   - зафиксированный набор и порядок вопросов/задач;
   - ответ пользователя;
   - результат и время выполнения.
4. `code_submissions`
   - пользователь и coding task;
   - исходный код;
   - статус выполнения;
   - stdout/stderr;
   - результат тестов и длительность.

Для контента использовать `draft`, `published`, `archived`. Удаление опубликованных материалов по умолчанию должно быть мягким: архивирование вместо физического удаления.

## API v1

Все endpoint начинаются с `/v1`. JSON имеет единый формат ошибок с `code`, `message` и необязательным `fields`.

### Чтение каталога

- `GET /v1/directions`
- `GET /v1/directions/{slug}`
- `GET /v1/directions/{slug}/tracks/{track}`
- `GET /v1/sections/{id}`
- `GET /v1/topics/{id}`
- `GET /v1/lessons/{id}`
- `GET /v1/questions/{id}`
- `GET /v1/coding-tasks/{id}`

Публичные read endpoint возвращают только `published`-контент и никогда не отдают эталонные решения или скрытые тесты.

### Прогресс

- `GET /v1/me/progress`
- `PUT /v1/me/progress/{contentType}/{contentId}`
- `GET /v1/me/activity`

Обновление прогресса должно быть идемпотентным.

### Мок-интервью

- `POST /v1/interview-sessions`
- `GET /v1/interview-sessions/{id}`
- `PUT /v1/interview-sessions/{id}/items/{itemId}`
- `POST /v1/interview-sessions/{id}/complete`

Сервер обязательно валидирует ограничения:

- теория: от 1 до 20 вопросов;
- лайвкодинг: от 1 до 10 задач.

Набор заданий фиксируется при создании сессии и не меняется после перезагрузки страницы. По возможности не повторять недавно использованные задания и распределять выбор по темам и сложности.

### Запуск кода

- `POST /v1/submissions`
- `GET /v1/submissions/{id}`

Скрытые тесты выполняются только на backend. Клиент получает итог по тестам, stdout/stderr и безопасное диагностическое сообщение, но не содержимое скрытых тестов и не эталонное решение.

### Админ-панель

Для `directions`, `tracks`, `sections`, `topics`, `lessons`, `questions`, `coding-tasks` и `coding-task-tests` нужны admin CRUD endpoint:

- список с фильтрами и пагинацией;
- создание;
- получение draft-версии;
- редактирование;
- изменение порядка;
- публикация/снятие с публикации;
- архивирование и восстановление.

Точные пути фиксируются в OpenAPI до подключения форм frontend. Массовый импорт допустимо добавить после стабильного одиночного CRUD.

## Админ-панель

Закрытая страница `/admin` должна позволять:

- перемещаться по дереву `направление -> трек -> раздел -> тема`;
- создавать и редактировать уроки, вопросы и coding tasks;
- редактировать Markdown с preview;
- выбирать Swift или Go для coding task;
- задавать starter code, эталонное решение и тесты;
- менять порядок элементов;
- сохранять draft и отдельно публиковать;
- фильтровать материалы по типу, статусу, языку, теме и сложности;
- видеть предупреждение перед архивированием;
- открывать опубликованную сущность в пользовательском интерфейсе.

Обычный пользователь не должен видеть элементы управления контентом. Скрытие кнопок на frontend не заменяет серверную проверку роли.

## Авторизация и безопасность

- На первом этапе Learny остаётся личным приложением с одним администратором, но схема поддерживает будущих пользователей.
- Использовать уже доступную идентичность Sites/ChatGPT в same-origin route handlers.
- BFF должен передавать Go API подписанные или служебно аутентифицированные данные, а Go API — независимо проверять подпись и роль.
- Никогда не доверять `userId`, `email`, `role` и admin-флагу из JSON, query string или произвольного browser header.
- Admin-доступ ограничивается server-side allowlist/ролью в базе.
- Все write endpoint требуют авторизацию и проверку роли/владения.
- Для записей использовать строгую валидацию, ограничения размера body и rate limiting.
- SQL выполняется параметризованно.
- Секреты, DSN, ключи runner и allowlist не коммитятся; добавить `.env.example` без значений.
- CORS не открывать через `*`; основной browser flow должен оставаться same-origin через BFF.
- Не логировать access tokens, cookies, эталонные решения и содержимое скрытых тестов.
- Для критичных admin-операций хранить audit log после завершения MVP CRUD.

## Безопасный запуск Swift и Go

Запуск недоверенного кода нельзя выполнять внутри процесса основного Go API.

Этапы:

1. В MVP Go API проксирует запрос к внешнему sandbox runner и сохраняет submission/result.
2. API ограничивает размер кода, язык, время, память, частоту запросов и число одновременных запусков.
3. После стабилизации заменить публичный runner на контролируемый сервис/изолированные контейнеры без исходящего интернета, с read-only filesystem, непривилегированным пользователем и жёстким timeout.
4. Версии Swift и Go должны быть явно зафиксированы и отображаться в редакторе.

Нельзя передавать runner секреты из пользовательского кода или возвращать пользователю внутренние команды и инфраструктурные ошибки.

## Миграция текущего frontend

Сейчас учебный контент находится в `app/StudyPlatform.tsx`, прогресс и пользовательские разделы — в `localStorage`, а `/api/run` напрямую использует Judge0.

Миграция выполняется постепенно:

1. Вынести текущие направления, модули, вопросы, уроки и coding tasks в seed/import данные backend.
2. Сохранить стабильные slugs, чтобы существующая навигация не сломалась.
3. Подключить frontend к read API и оставить временный fallback только на время перехода.
4. После проверки удалить захардкоженный учебный контент из React-компонента.
5. Один раз импортировать локальный прогресс авторизованного пользователя через идемпотентный endpoint, затем пометить миграцию завершённой.
6. Удалить `learny-sections` и `learny-completed` как источники истины; локально можно оставить только черновик кода до отправки.
7. Перенести `/api/run` на новый submissions API после готовности runner-модуля.

Во время миграции уже опубликованный пользовательский интерфейс должен продолжать работать.

## План реализации

### Этап 0. Контракт и baseline

- Зафиксировать текущие пользовательские сценарии и данные frontend.
- Описать OpenAPI v1 и правила ошибок.
- Подготовить `backend/`, `go.mod`, конфигурацию и health endpoints.
- Добавить Docker Compose для локального PostgreSQL и `.env.example`.
- Настроить команды разработки и проверки, не ломая существующие npm scripts.

Готово, когда Go API запускается локально, `/healthz` и `/readyz` отвечают корректно, а OpenAPI проходит валидацию.

### Этап 1. База и каталог

- Создать первую SQL-миграцию.
- Реализовать repositories/services для каталога.
- Добавить seed с текущими iOS/Go материалами.
- Реализовать read API только для опубликованного контента.
- Добавить integration tests с настоящим PostgreSQL.

Готово, когда весь текущий каталог можно получить из Go API и порядок элементов совпадает с интерфейсом.

### Этап 2. Подключение frontend

- Добавить typed API client и BFF route handlers.
- Заменить захардкоженные каталоги, темы, вопросы и задачи данными API.
- Добавить loading, empty и retry/error состояния без изменения согласованного дизайна.
- Не допускать полного падения страницы при временной недоступности API.

Готово, когда пользовательские страницы полностью отображаются из PostgreSQL, а React больше не является источником учебного контента.

### Этап 3. Админка и CRUD

- Защитить `/admin` и admin API.
- Реализовать дерево каталога и формы контента.
- Добавить draft/publish/archive и изменение порядка.
- Реализовать редактор coding task и тестов.
- Добавить серверную валидацию и понятные ошибки форм.

Готово, когда новый вопрос или задача создаётся из `/admin`, публикуется и без нового deploy появляется в нужном разделе Learny.

### Этап 4. Пользовательский прогресс

- Реализовать `user_progress` и activity API.
- Подключить экран прогресса и отметки выполнения.
- Выполнить одноразовый импорт данных из `localStorage`.
- Проверить идемпотентность и восстановление после перезагрузки.

Готово, когда прогресс хранится между устройствами и больше не зависит от конкретного браузера.

### Этап 5. Мок-интервью

- Реализовать создание и восстановление interview session.
- Валидировать лимиты 20/10 на сервере.
- Добавить выбор без нежелательных повторов и со смешением тем.
- Сохранять ответы, код, состояние и финальный результат.
- Подключить существующие экраны теории и лайвкодинга к session API.

Готово, когда интервью можно продолжить после перезагрузки, а набор вопросов остаётся тем же.

### Этап 6. Компиляция и проверка задач

- Реализовать submissions API и адаптер внешнего sandbox runner.
- Перенести лимиты, нормализацию результата и обработку ошибок в Go.
- Добавить выполнение открытых и скрытых тестов.
- Сохранять попытки и связывать успешный результат с прогрессом.
- Добавить rate limiting, concurrency limit и timeout.

Готово, когда Swift/Go код запускается через Go backend, скрытые тесты не попадают в browser, а недоступность runner корректно обрабатывается.

### Этап 7. Production и эксплуатация

- Развернуть Go API и managed PostgreSQL отдельно от Sites frontend.
- Настроить секреты, HTTPS, BFF URL и закрытый доступ между frontend и API.
- Выполнять миграции отдельным release step, не автоматически из каждого API instance.
- Добавить резервное копирование PostgreSQL и проверку восстановления.
- Добавить request ID, структурированные логи, health checks и уведомления об ошибках.
- Провести security review admin и runner endpoint.

Готово, когда новый deploy безопасно накатывает миграции, backend наблюдаем, база резервируется, а frontend использует production API.

## Приоритет поставки

Первый полезный backend MVP — этапы 0–3. Его результат: все материалы лежат в PostgreSQL, frontend читает их через Go API, а `londxz` может добавлять и публиковать вопросы через админку.

После MVP порядок такой:

1. прогресс;
2. мок-интервью;
3. submissions и скрытые тесты;
4. расширенная аналитика, импорт и audit log.

Не начинать с собственного container runner: сначала завершить контентный backend и админку.

## Тестирование

- Unit tests для бизнес-правил, лимитов и выбора вопросов.
- Integration tests repositories и migrations на PostgreSQL.
- HTTP tests для успешных сценариев, валидации, 401, 403, 404 и конфликтов.
- Contract tests между OpenAPI, BFF и Go API.
- E2E минимум для цепочек:
  - admin создаёт и публикует вопрос;
  - пользователь открывает опубликованный вопрос;
  - пользователь сохраняет прогресс;
  - теория создаёт сессию максимум из 20 вопросов;
  - лайвкодинг создаёт сессию максимум из 10 задач;
  - код отправляется и возвращает результат.
- Существующие `npm test` и production build frontend должны продолжать проходить.

## Definition of Done для каждой backend-задачи

- Есть миграция для изменения схемы.
- Есть серверная валидация и проверка авторизации.
- OpenAPI обновлён.
- Добавлены релевантные unit/integration tests.
- Ошибки не раскрывают секреты и внутренности инфраструктуры.
- Нет новых авторитетных данных в `localStorage`.
- Frontend имеет loading/error/empty состояния.
- Не нарушены существующий liquid-glass дизайн и мобильная адаптация.
- README обновлён, если изменились запуск, переменные окружения или deploy.

## Ограничения и принципы

- Не хранить вопросы и задачи в frontend после завершения миграции.
- Не давать frontend доступ к эталонным решениям и скрытым тестам.
- Не смешивать admin CRUD с пользовательскими endpoint без проверки роли.
- Не делать физическое удаление опубликованного контента обычным действием.
- Не выполнять пользовательский код в API-процессе.
- Не коммитить секреты и production DSN.
- Не менять согласованный бело-чёрный liquid-glass стиль ради backend-функций.
- Сначала закончить надёжный CRUD и подключение frontend, затем усложнять систему.
